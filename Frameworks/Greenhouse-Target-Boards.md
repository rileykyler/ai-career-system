# Greenhouse Target Boards

Greenhouse has no cross-company job search. Its public data is exposed one employer at a time, through a board token:

```
https://boards-api.greenhouse.io/v1/boards/<token>/jobs?content=true
```

That endpoint is public, unauthenticated, and returns the **full job description text** in the `content` field — which means Greenhouse-sourced listings never hit the `get_job_details` rate limit that has capped the Indeed leg of the scan on 2026-09-11 through 09-14. Fetch it with WebFetch; direct `curl` from the container is blocked by the egress proxy.

This file is the list the daily scan walks each morning. It is a living document — add, remove, or re-rank companies whenever your targeting shifts, and tell Claude in a normal project chat if you want a company added.

## Fetch-approval gate — read this before calling the API (added 2026-09-15)

`boards-api.greenhouse.io` (and a board's bare index page, `job-boards.greenhouse.io/<token>` with no job id) sit behind a WebFetch provenance/approval step. In a live, interactive session that step resolves and the fetch goes through normally — confirmed working 2026-09-15. In a **scheduled/unattended run there is no one to answer the approval prompt, so it times out and every single call fails with `PROVENANCE_REQUIRED`**, even on immediate retry of the exact same URL — this was confirmed by repeated retries on 2026-09-15, and it is a session-liveness issue, not a bad token, a rate limit, or a proxy/network problem, so retrying it doesn't help and just burns calls.

**How to tell which situation you're in:** try one `boards-api.greenhouse.io` call. If it returns real job data, you're in a live/interactive context — keep using the API endpoint per "How the daily run uses this list" below, since it's the more complete method. If it returns `PROVENANCE_REQUIRED`, stop calling that endpoint for the rest of the run (don't retry it board-by-board — one failure means all 29 will fail) and switch immediately to this fallback for every remaining board:

1. `WebSearch` for `site:job-boards.greenhouse.io/<token>` (add a role keyword if the token is a large company with hundreds of reqs, e.g. Capco or Motive, to bias results toward relevant titles).
2. Read candidate job titles, ids, and URLs out of the search-result snippets.
3. `WebFetch` each individual `https://job-boards.greenhouse.io/<token>/jobs/<id>` posting page directly (not the board index) — this specific page pattern is **not** gated and reliably returns full job text even in an unattended run.
4. Occasionally an individual posting URL returns the board's directory listing instead of the specific job (stale id, or a very large shared board like Capco's ~700 global reqs) rather than `PROVENANCE_REQUIRED` — that's a different, ordinary failure; treat it like any other unverifiable listing and log it to Jobs-Seen-Log.md's "Needs follow-up" section rather than guessing from the title.

This fallback is slightly less complete than the API (one WebSearch + one WebFetch per candidate instead of one WebFetch per whole board, and it only surfaces whatever WebSearch's index has picked up), but it is the only path that actually works unattended, so it's the default assumption for the daily scheduled run — try the API first since it's free to check, but don't burn a whole run's time budget on it once it's confirmed blocked.

## How the daily run uses this list

1. Fetch each token's `?content=true` feed — or, if that returns `PROVENANCE_REQUIRED` (see above), use the WebSearch + individual-posting-WebFetch fallback for every remaining board this run.
2. Keep only postings whose location is Texas (Austin, San Marcos, Houston, Dallas, San Antonio) or explicitly US-remote.
3. Drop anything already in `Jobs-Seen-Log.md` (match on the Greenhouse job URL, then on company + title).
4. Score survivors against `Job-Fit-Scoring-Rubric.md` using the full `content` text — no preview-data guessing, since the text is always there.
5. A 404 on a token means the company renamed or left Greenhouse. Skip it silently, note it in the run summary, and it gets pruned from this file later.

## Finding new boards

Greenhouse board tokens are discoverable by domain-scoped web search rather than guessing. Guessing is unreliable — `basepowercompany`, `voltus`, `lancium`, `formenergy`, `crusoeenergy` and `jupiterpower` all 404'd on 2026-09-15 while the tokens above resolved.

Use WebSearch restricted to `job-boards.greenhouse.io` and `boards.greenhouse.io` with a role-and-place query, then read the token out of the result URL (`job-boards.greenhouse.io/<token>/jobs/...`). Queries that produced this list:

- `energy storage ERCOT Austin Texas careers analyst`
- `power markets trading analyst Houston Austin jobs`
- `retail electricity provider commercial operations analyst Texas`
- `data center power infrastructure analyst operations Texas`
- `sales development representative Austin Texas SaaS entry level`
- `business development representative BDR entry level software company`

The daily run does one or two of these discovery searches per morning, rotating the query, and appends any newly found token to this file with a one-line note on why.
